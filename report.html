1. Goals and Purpose of the Exercise

The objective of Exercise 2 is to design, implement, and integrate an end-to-end database-backed software system for medical personnel management. The assignment comprises two tightly linked components:

  • Exercise 2-1 (Core Database Engine & CRUD Operations): Focuses on using Python's built-in sqlite3 module to create a local relational database for storing doctor records. The goal is to author modular, reusable functions executing core CRUD operations (Create, Read, Update, Delete) with strict transaction management and SQL safety principles (preventing SQL injection via parameterized statements).
  • Exercise 2-2 (Web Application Interface): Focuses on developing a modern, responsive web application using the Flask micro-framework. The application connects directly to the SQLite database established in Exercise 2-1, providing an intuitive Graphical User Interface (GUI) where hospital administrators can submit doctor records through validated HTML forms and inspect structured tabular views across dedicated web pages.
Project Architecture Strategy: To adhere to software engineering best practices (Separation of Concerns), the codebase is organized as two distinct sub-projects under a unified repository: Exercise_2_1/ contains zero-dependency database scripts, while Exercise_2_2/ encapsulates the Flask web server, helper modules, and Jinja2 templates.

2. Detailed Description of the Algorithm and Approach

2.1. Database Schema Specification

Both exercises interact with the doctors.db SQLite database. A table named doctors was designed with the following relational schema:

Column Name Data Type Constraints Description
id INTEGER PRIMARY KEY AUTOINCREMENT Unique auto-incrementing doctor identifier
first_name TEXT NOT NULL Doctor's given name
last_name TEXT NOT NULL Doctor's family name
joining_date TEXT NOT NULL ISO 8601 formatted date string (YYYY-MM-DD)
salary REAL NOT NULL Doctor's monthly salary (floating point numeric)
address TEXT NULLABLE Clinic or residential address

2.2. Exercise 2-1: Algorithmic Approach & CRUD Design

In Exercise_2_1/doctors_db.py, database interactions are structured using Python's context manager (with sqlite3.connect(...) as conn). This guarantees that connections are closed deterministically and transactions are committed automatically upon successful block execution, or rolled back if an exception occurs.

  1. Table Creation (create_table): Executes DDL query CREATE TABLE IF NOT EXISTS doctors (...) ensuring idempotency without errors on subsequent runs.
  2. Record Insertion (insert_doctor): Executes a parameterized INSERT INTO doctors VALUES (?, ?, ?, ?, ?) statement using tuple binding to prevent SQL injection vulnerabilities. Returns cursor.lastrowid.
  3. Data Querying (get_all_doctors & get_doctor_by_id): Executes SELECT * FROM doctors, returning a list of rows or a single record via fetchone().
  4. Record Modification (update_doctor): Executes parameterized UPDATE doctors SET ... WHERE id = ?, returning cursor.rowcount to verify modification.
  5. Record Removal (delete_doctor): Executes parameterized DELETE FROM doctors WHERE id = ?.
  6. Formatted Console Output (display_doctors): Formats doctor records into aligned columns with currency notation ({:,.2f}).

2.3. Exercise 2-2: Flask Web Architecture (MVC Pattern)

The web application in Exercise_2_2 is structured following the Model-View-Controller (MVC) architectural pattern:

  • Model (db_helper.py): Encapsulates all data access logic. Configures conn.row_factory = sqlite3.Row, enabling column access by attribute name (e.g., doctor['first_name']) within Jinja2 templates.
  • Controller (app.py): Routes client HTTP requests, validates incoming form payloads, coordinates with db_helper, and directs responses using the Post/Redirect/Get (PRG) pattern to prevent accidental duplicate form submissions upon page reload.
  • View (templates/): Rendered with Bootstrap 5 for clean aesthetics and responsive mobile-first grid layouts.
    • base.html: Shared layout containing top navbar, alert container, and footer.
    • doctor_list.html: Tabular view listing all doctors with formatted salaries, action buttons (Edit, Delete), and a "+ Add New Doctor" CTA.
    • add_doctor.html: Dual-purpose form handling both New Creation and Existing Record Updates.
